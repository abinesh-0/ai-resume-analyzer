# Security Policy

This is a student/portfolio project that handles **real personal documents**
(resumes) and **email credentials**. Security matters more here than in a
typical demo app.

---

## Supported versions

| Version | Supported |
| ------- | --------- |
| `1.x`   | ✅        |

---

## Reporting a vulnerability

Please **do not open a public issue** for security problems. Public reports
expose every deployed instance before a fix exists.

Instead, open a [private security advisory][advisory] on this repository, or
contact the maintainer through their GitHub profile.

[advisory]: https://github.com/abinesh-0/ai-resume-/security/advisories/new

You should receive a response within a few days. Please give a reasonable
window before disclosing anything publicly.

## :no_entry_sign: Never commit these

The repository must stay safe to push. These belong in `.env` only, which
`.gitignore` already blocks:

| Secret | Variable |
| ------ | -------- |
| Flask session key | `SECRET_KEY` |
| MySQL password | `DB_PASSWORD` |
| Gmail App Password | `MAIL_PASSWORD` |
| Gmail account address | `MAIL_USERNAME` |

**Generated by:**

```bash
python -c "import secrets; print(secrets.token_hex(32))"
```

If a secret is ever committed, treat it as compromised: revoke the Gmail App
Password, rotate the database password, and regenerate `SECRET_KEY` (which
invalidates all active sessions).

---

## :no_entry_sign: Never upload real documents to the repo

`uploads/` is ignored for a reason.

- Do not commit resumes — your own or anyone else's.
- Do not commit screenshots that reveal real names, phone numbers, email
  addresses, or employer names. Use a **synthetic sample resume** for demos,
  screenshots, and GIFs.
- Do not commit database dumps. `database.sql` contains schema only — keep it
  that way.
- Files already in `uploads/` on your machine get deleted routinely; never
  stage them with `git add -A` without checking `git status` first.

## How the application protects users

These protections are implemented in `app.py`:

| Control | Implementation |
| ------- | -------------- |
| Password storage | Salted hashes via `werkzeug.security.generate_password_hash` — plaintext is never stored |
| OTP storage | Hashed in `otp_tokens.otp_hash`; raw OTP exists only inside the email |
| OTP lifetime | 90 seconds (`OTP_EXPIRY_SECONDS`) |
| OTP attempts | Locked after 5 tries (`OTP_MAX_ATTEMPTS`) |
| OTP reuse | Single use — `consumed_at` is stamped on success |
| Resend throttling | 30-second cooldown (`OTP_RESEND_COOLDOWN_SECONDS`) |
| Upload type | Restricted to `.pdf` and `.docx` (`ALLOWED_EXTENSIONS`) |
| Upload size | Capped at 10 MB (`MAX_CONTENT_LENGTH`) |
| Filenames | `secure_filename()` + random UUID storage name — blocks path traversal and collisions |
| Authorization | `@login_required` on analysis, history, and profile routes |
| Ownership | History and profile queries are always scoped to `session["user_id"]` |
| SQL | Parameterised queries throughout; no string-built SQL |
| Email | TLS on port 587 |

## Known limitations

Being honest about these is part of using the project safely:

- Uploaded resumes are **stored on the server disk** in `uploads/`. This is
  acceptable for a local portfolio app, not for a public multi-tenant service.
- Session cookies need `SESSION_COOKIE_SECURE` and `SESSION_COOKIE_HTTPONLY`
  configured before serving over HTTPS.
- The repo ships no rate limiting on `/login`, `/register`, or `/resend-otp`
  beyond the OTP cooldown.
- `SECRET_KEY` falls back to a `"dev-only-change-me"` default when unset.
  **Never deploy with the default.**
- The bundled ML model is a small demo artifact; see
  [`docs/ml-pipeline.md`](docs/ml-pipeline.md).

## Hardening before any public deployment

1. `FLASK_DEBUG=false` and a strong random `SECRET_KEY`.
2. Serve behind HTTPS with a production WSGI server (Waitress, gunicorn).
3. Set `SESSION_COOKIE_SECURE = True`, `SESSION_COOKIE_HTTPONLY = True`.
4. Add a CSP and `X-Frame-Options` / `X-Content-Type-Options` headers.
5. Purge `uploads/` on a schedule, or store objects with short-lived expiry.
6. Add login and registration rate limiting.
7. Use a dedicated MySQL user with least privilege — not `root`.
